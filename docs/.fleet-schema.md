# Fleet `.fleet/` Schema (v1.0)

**Purpose:** Minimal, consistent metadata structure for 20–40 repository portfolio.

**Key principle:** Compliance is structural (files exist, schema valid); standards are behavioral (coding rules, governance constraints). This schema ensures compliance; standards are defined in `fleet-base/docs/STANDARDS.md`.

---

## Quick Definition

- **Compliance** = "Does my repo have the right `.fleet/` files with valid YAML and required fields?" (technical/structural check)
- **Standards** = "Does my code follow layering, naming, governance rules?" (human/team behavior)
- **Connection** = `.fleet/` files document that your repo follows standards; compliance validates the documentation exists.

---

## Required Files (All Active Repos)

### 1. `.fleet/config.yaml` (Repo Metadata & Settings)

**Purpose:** Repository type, language, testing strategy, standards expectations, governance configuration.

**Required fields:**
- `type` — one of: `library`, `infrastructure`, `service`, `tooling`, `research`, `operations`
- `language` — one of: `python`, `go`, `typescript`, `rust`, etc.
- `schema_version` — must be `'1.0'`

**Recommended fields:**
- `layer` — if applicable: `0` (shared), `1` (orchestration), `2` (applications)
- `description` — one sentence on repo purpose
- `test_framework` — e.g., `pytest`, `jest`
- `owner` — GitHub handle or email (matches catalog-info.yaml)

**Optional fields:**
- `standards.type_hints` — e.g., `required`, `recommended`
- `standards.docstrings` — e.g., `google-style`, `pep257`
- `standards.max_line_length` — e.g., `120`
- `testing.min_coverage` — e.g., `80`
- `guard_rails.*` — limits on changesets (e.g., `max_lines_changed`, `max_files_changed`)

**Minimal example (20 lines):**
```yaml
type: library
language: python
schema_version: '1.0'
layer: 0
description: Shared infrastructure for fleet operations
owner: mark@example.com
test_framework: pytest
testing:
  min_coverage: 80
  test_command: pytest tests/
standards:
  type_hints: required
  docstrings: google-style
  max_line_length: 120
```

**When to expand:** Add governance/audit sections only if your repo has special rules (e.g., auto-fix policies, compliance audit logging). See fleet-agents/.fleet/config.yaml for a comprehensive example.

### 2. `.fleet/catalog-info.yaml` (Backstage Metadata)

**Purpose:** Component registry for dependency tracking, API export, ownership.

**Format:** Backstage v1alpha1 Component kind ([spec](https://backstage.io/docs/features/software-catalog/descriptor-format))

**Required fields:**
- `apiVersion: backstage.io/v1alpha1`
- `kind: Component`
- `metadata.name` — repo name (lowercase, matches GitHub repo)
- `metadata.description` — one-liner
- `spec.type` — one of: `library`, `service`, `infrastructure`, etc.
- `spec.lifecycle` — one of: `experimental`, `production`, `deprecated`, `archived`
- `spec.owner` — GitHub handle or email

**Recommended fields:**
- `spec.dependsOn` — list of fleet repos this repo depends on, in format `component:repo-name`
- `spec.provides` — list of exported APIs/modules
- `metadata.labels` — map of `layer`, `type`, `language`, etc.

**Minimal example (18 lines):**
```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: my-repo
  description: What this repo does (one sentence)
  labels:
    layer: '1'
    type: library
    language: python
spec:
  type: library
  lifecycle: production
  owner: mark@example.com
  dependsOn:
    - component:fleet-base
  provides:
    - MyClass
    - my_function
```

**When to expand:** Add `tags`, `responsibilities`, `relationships` if you need to document cross-repo impact. See fleet-ops/.fleet/catalog-info.yaml for full example.

### 3. `.fleet/boundaries.yaml` (Architectural Boundaries & Invariants)

**Purpose:** Document repo boundaries, invariants (e.g., layer constraints), and verification status.

**Use case:** At L1 or L2, document import restrictions, data contracts, or deployment invariants.

**Minimal structure:**
```yaml
schema_version: '1.0'
name: my-repo
description: Boundary specification
status: declared

invariants:
  - id: NO_L2_IMPORTS
    description: Layer 1 must not import Layer 2
    mechanism: import-linter
    local_command: just check-layers
    local_status: passing
```

**When to include:** Required for L1+ repos; optional for L0 libraries. At minimum, state `status: declared` and list any import/data constraints.

**Verification section (optional):** Add once verified by audit:
```yaml
verification:
  status: baseline-audited
  audited_ref: <commit-sha>
  audit_artifact: <path-to-audit-report>
  verified_claims:
    - "Layer boundary enforcement passes"
```

See fleet-ops/.fleet/boundaries.yaml for comprehensive example.

## Optional Files (Recommended)

### 4. `.fleet/roadmap.yaml` (if applicable)

**Purpose:** Milestone tracking and planned work.

Use if your repo has cross-fleet impact or long-running initiatives.

### 5. `.fleet/health.yaml`

**Purpose:** Metrics pointers and last health check.

**Simple example:**
```yaml
schema_version: '1.0'
metrics:
  ci_dashboard: https://github.com/baseline0/my-repo/actions
  coverage_report: coverage/index.html
last_health_check: '2026-09-26T14:00:00Z'
```

### 6. `.fleet/maintenance.md` or `.fleet/onboarding.md`

**Purpose:** Documentation specific to repo maintenance or onboarding.

Keep these brief; link to root-level docs where possible.

---

## Note on Extra Files

The validator allows additional `.fleet/` files beyond the required/optional set. However, avoid accumulating documentation in `.fleet/` — it's for metadata, not detailed guides. Use your root `README.md`, `docs/`, and GitHub Wiki for narrative documentation. Example of what NOT to do:

- ❌ `.fleet/BOUNDARIES.md` + `.fleet/boundaries.md` + `.fleet/boundaries.yaml` (pick one: YAML is authoritative, .md is linked narrative)
- ❌ `.fleet/dependencies.yaml` (use `catalog-info.yaml` spec.dependsOn instead)
- ❌ `.fleet/all-our-detailed-runbooks.md` (use `docs/runbook.md` in repo root)

---

## Files NOT in `.fleet/` (Live Elsewhere)

These belong in the repo root or `docs/`:

- `README.md` — must answer: what, who, how to build/test, how to release, health status link
- `CONTRIBUTING.md` — how to safely make changes, review process, CI entry points
- `BOUNDARIES.md` — detailed boundary rationale (linked from `.fleet/boundaries.yaml`)
- `docs/ARCHITECTURE.md` — design decisions, data flow, dependency rationale
- `docs/RUNBOOK.md` — incident response and recovery
- `.github/pull_request_template.md` — GitHub PR template
- `CODEOWNERS` — code review routing (GitHub)

## Validation

Run to check compliance across all repos:
```bash
# All repos
just check-governance-strict

# Single repo
just check-governance-repo my-repo

# JSON output (for automation)
just check-governance-json
```

**What's checked:**
- Schema version is `'1.0'`
- Required files present (config.yaml, catalog-info.yaml, boundaries.yaml)
- Required fields in each file are non-empty
- No YAML syntax errors

## Fleet Inventory (Source of Truth)

Central record of all repos in the fleet:
- 📍 Location: `fleet-ops/fleet-manifest.yaml` or `fleet-coordination/fleet-inventory.yaml`
- Contains: repo name, purpose, owner, layer, lifecycle, criticality
- Updated: monthly via `just governance-report-monthly`
- Reference: Each repo's `.fleet/config.yaml` should match the inventory record

## Schema Evolution

**Current version:** `1.0` (2026-09-26)

When adding new fields:
1. Add to one repo's `.fleet/` files first (pilot).
2. Run `check-governance` to confirm validation still passes.
3. Document new field in this schema.
4. Update all repos incrementally (no big-bang migration).

## Questions?

- **"What if my repo doesn't fit these types?"** → Use `tooling` or `research` and document in `.fleet/config.yaml` description.
- **"Do I need boundaries.yaml if I'm L0?"** → Recommended but not required. Use if you have import or data constraints.
- **"How often do I update these files?"** → `config.yaml` and `catalog-info.yaml` change when repo type/ownership changes (rare). `boundaries.yaml` updates when invariants shift. Update inventory monthly.
- **"What's the difference between owner in config.yaml vs. catalog-info.yaml?"** → They should match; both point to the same GitHub handle or email. Maintaining both is redundant but expected for now (config is operational, catalog-info is Backstage-standard).
